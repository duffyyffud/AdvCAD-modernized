# AdvCAD デバグ メタ知識

このワークスペース固有の、advcad(C++本体)のデバグに関する一般則をまとめた文書。
対象は個別の不具合の事実そのものではなく、他の不具合にも転用できる一般則。
個別の不具合の記録は`CLAUDE.md`の「Systematic Debugging Breakthroughs」を見る事。

## 1. 解決済み不具合から抽出した一般則

### 1-1. 閾値の境界そのものにバグが潜む
Face 5は「ちょうど6ノード」の面だったが、robust CDTを使うかどうかの判定が`> 6`だった為に対象から漏れ、通常の三角形分割に回されて混合三角形を生んだ(commit `7c1e226`)。
数値閾値を使う判定を書く・見直す時は、境界値と厳密に一致するケースを明示的にテスト対象へ加えないと見逃す。

### 1-2. 新しい処理経路を追加する時、旧経路が担っていた副次的な後始末を引き継がせ忘れる
robust CDTが生成する三角形には、通常経路が行っていたdomain IDの割り当てが行われておらず、`domainId==0`という既存のフィルタ条件によって静かに除外されていた。結果として`doSmoothing()`側で「三角形配列が空」という、一見無関係な症状としてassertion failureが現れた(commit `7c1d651`)。
新しい処理経路を追加する時は、旧経路が暗黙に行っていた後始末(ID付与・状態初期化等)を新経路でも行っているか、下流の全ての前提条件を洗い出して確認する必要がある。

### 1-3. 「危険な入力」を検出する軸は1つとは限らない
複雑さ(ノード数・境界セグメント数)とは独立に、座標の絶対値の小ささ(数値精度の危うさ)も別の危険軸として存在した(commit `f0d9ab5`)。ノード数だけを見る判定では、小規模座標由来の失敗を見逃す。
危険な入力を判定するロジックを作る時は、軸が複数あり得る事を前提に、それぞれ独立に検出条件を持たせる。

### 1-4. assertion failureは即アルゴリズムのバグと決め付けない、まず入力データの妥当性を疑う
残っていた2件の失敗はadvancing frontのアルゴリズム欠陥に見えたが、実際は重複頂点・零長辺という不正な入力形状が原因だった(commit `efca872`)。同じスタックトレース・同じassertion文言でも、原因は「アルゴリズムの欠陥」と「入力データの不正」の2種類あり得る。
assertion failureを見た時は、まず`validate_geometry.py`のような入力検証を先に行い、入力側の妥当性を確定させてからアルゴリズム側を疑う順序にする。

### 1-5. 完全に壊れたモデルより、動くモデルを狙って壊す方が速い
`mesh_failure_analyzer.py`は、既に動作しているモデルのメッシュサイズを段階的に振り、意図的に境界的な失敗を作り出す事で、再現性が高く原因を絞り込みやすい小さな失敗ケースを得た。
いきなり全滅しているモデルを最初から追うより、動いている物のパラメータを振って「動かなくなる境目」を探す方が、原因の絞り込みが速い。

### 1-6. 同種の防御コードは次元・実装ごとに独立して漏れる
3Dベクトルの零割り対策(`space3d_inline.cc`)は既にあったが、対称なはずの2D側(`space2d_inline.cc`)には無かった(commit `b64606a`)。
片方の実装(3D)で防御コードを見つけた・追加した時は、対称な別実装(2D)にも同様の防御が入っているか必ず確認する。同じ対策のはずが実装ごとに個別に漏れる。

### 1-7. 閾値緩和は必ず全回帰件数で再検証してから採用する
`> 6`→`>= 6`、`1e-3`→`1e-2`といった閾値の緩和は、いずれも19件全体の回帰確認で退行が無い事を確認してから採用されている(commit `7c1e226`・`f0d9ab5`のコミットメッセージに残る「成功率を維持しつつ」の記述より)。
判定条件を緩める変更は、対象ケースが直るかどうかだけでなく、それまで通っていた他の全件が引き続き通るかを必ず確認してから確定させる。

## 2. 段階的デバグ手順

出典: `~/workspace/wsPy/AutoDevByMultiAgents/prompts/CLAUDE_CODE_IdealPhasedTaskTemplate.md`(fork agentによる調査、2026-07-25)。advcad向けに書き直した。

- **Phase 0(事実の正本確認)**: 触れる事実ごとに、それを正しく示す唯一の場所(正本)を先に特定する。矛盾を見つけたら、直す前にまず所在を報告する。
- **Phase 1(前提の実在確認)**: 使うAPI・ファイル・行番号・現在の挙動を、憶測でなく`grep`・`Read`・実行で確認してから進める。
- **Phase 2(計画のみ提示・go待ち)**: 直し方の案を1つだけ提示し、実装する前に承認を得る。
- **Phase 3(最小実装)**: 提示した内容だけを実装する。関係の無い変更を混ぜない。
- **Phase 4(検証)**: ビルド・`dev/test_regression.py`(19件)を実際に実行し、直った事と退行が無い事の両方を確認する。
- **Phase 5(構造化した報告)**: 結論→根拠(commit・実行結果)→残課題、の順で報告する。

## 3. 累積再試行の打ち切り(エスカレート(棚上げ))基準

同一の不具合に対して、差し戻し・再試行が累積3回に達した時点で、それ以上その場での追跡を続けない。
その時点で分かっている事実・試して効かなかった事を整理して報告し、Akioへエスカレート(棚上げ)する。
根拠: 出典元(`AutoDevByMultiAgents`)にはこの基準があるが、AdvCAD側の`CHAT_OPERATIONS.md`には無い。`CLAUDE.md`の「Systematic Debugging Breakthroughs」は複数バージョン(v0.12.1〜v0.12.6)にわたる「直っては次の不具合が出る」を繰り返す記録であり、打ち切り基準が無いまま調査を続けてきた実例である。
